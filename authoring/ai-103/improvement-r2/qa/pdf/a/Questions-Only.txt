Case study - Rotor equipment reservations
Rotor rents industrial equipment to authenticated business customers. Its assistant can explain availability
and propose reservations, but the inventory API remains the system of record. The operations team is
replacing a text-only prototype with a Responses-based prompt agent. Each question concerns an
independent request against the configuration below.
Application and identity
The backend receives a signed application session identifying the customer and warehouse. It calls the
agent using one managed identity. Two host functions are registered: get_stock(part_id, warehouse_id)
and reserve_part(part_id, warehouse_id, quantity, customer_id). The stock function is read-only. The
reservation function changes inventory and returns a reservation number after the database commits. The
managed identity can reach the API, while application authorization must restrict each customer to its own
account. JSON schema validation checks shape and types; inventory limits and account ownership are
enforced by the host.
Action policy
A customer may request a proposal without committing it. Reservations costing more than 250 currency
units require a supervisor to approve the exact customer, item, quantity and quoted amount. An approval
for five units is not approval for fifty. A changed proposal must return to the approval screen. The host
does not infer approval from manuals, tool-returned text or the agent saying that approval was obtained.
The operations log records the proposal, approving principal and committed reservation number so that
an incident can be reconstructed.
Observed request
A request checks the same part at two warehouses. Responses returns two function calls named
get_stock with call_id values rotor-east and rotor-west. The west warehouse replies first. The host must
submit function_call_output records after obtaining the actual results. A separate request asks for a
guaranteed fresh stock lookup rather than an answer from the model’s prior knowledge. Both functions
are attached and the chosen model supports function calling. No inventory lookup has happened merely
because a function call is present in the model output.
Failure investigation
A test customer asks for a reservation belonging to another customer account. The argument object
passes the JSON schema. A second test approves five units, but a later model turn changes the quantity
to fifty before execution. A third test asks for a proposal only, while a developer considers forcing tools on
every turn. Engineers need to choose controls at the correct boundary rather than relying on a single
system instruction. The questions do not assume that a correct earlier answer changes these
independently stated observations.
Diagnostic exhibit
Request exhibit: {"calls":[{"name":"get_stock","call_id":"rotor-east"},{"name":"get_stock","call_id":"rotor-
west"}],"completionOrder":["rotor-west","rotor-east"]}. The reservation tests are separate requests, not
effects of this lookup.

Case study - Harbor maintenance knowledge
Harbor maintains manuals for several equipment departments. Its new assistant must answer policy and
catalog questions with current evidence and distinguish factual support from useful but unrelated prose.
Search, embedding and generation are separately observable components. Each child question uses the
same architecture and an independent observation.
Corpus and index
The Search index stores chunk text, a filterable department field, a catalog identifier and one vector field.
Maintenance staff often search by exact identifiers such as HX-104 as well as by descriptions of
symptoms. The current corpus was embedded with deployment harbor-embed-x. A proposed query
deployment harbor-embed-y has the same vector dimensions but uses an unrelated model. The index is
not automatically regenerated when a developer changes a query-time setting. The source documents
and their department labels are authoritative.
Access and retrieval
The application authenticates each employee and derives an allowed department from its own
authorization service. Department boundaries apply before evidence is returned to the model. A
generated instruction asking the model to ignore unauthorized passages is not the access filter. The team
can configure keyword retrieval, vector retrieval and hybrid retrieval. An optional semantic reranker
operates on retrieved candidates; it does not create content embeddings or rename index fields. Query
vectors must be compatible with the content vectors being searched.
Evaluation evidence
A held-out test includes queries, relevance judgments for candidate documents, retrieved passages and
generated answers. One passage says the repair warranty lasts twelve months. An answer says twenty-
four months while staying on the user’s topic. Another answer quotes the twelve-month passage correctly
but responds to a shipping-time question. The team wants separate measurements for retrieval quality,
contextual support and response relevance rather than one total score. A successful query response
establishes transport success, not answer correctness.
Operations
Indexer logs record document-level errors and warnings. An overall successful run still requires checking
whether required documents entered the index. An embedding model change needs a planned reindexing
path and evaluation before rollout. Engineers retain safe request identifiers to correlate Search requests
with agent traces. They do not put service credentials in model-visible tool errors. A reviewer should
combine the named corpus, access and evaluation facts to choose each answer; previous child answers
are not prerequisites and do not alter the configuration in this case.
Diagnostic exhibit
Evaluation exhibit: {"contentEmbedding":"harbor-embed-x","queryEmbedding":"harbor-embed-
y","dimensionsMatch":true,"passageWarrantyMonths":12,"answerWarrantyMonths":24}. The authorized
department is derived from the employee session, not either deployment name.

Case study - Lumen regional engineering assistant
Lumen operates an engineering assistant for staff in the European Union. Its platform team is designing
deployment, identity and retrieval controls together, with separate principals for deployment and runtime.
The service must answer interactively and retain existing learner and operational records during the
migration described here.
Workload boundary
The processing policy permits inference across EU countries but forbids processing outside that data
zone. Interactive requests cannot wait for a nightly batch. Demand varies across the day and procurement
wants on-demand token billing rather than reserved throughput. The selected model is available for every
deployment family considered in the questions, and the relevant quota has already been confirmed. The
resource’s region alone is not the organization’s definition of the inference processing boundary.
Inference identity
The backend calls an Azure OpenAI resource through its /openai/v1/ endpoint using Microsoft Entra
credentials. Its runtime managed identity currently has Reader on that resource and no inference data
role. Token acquisition succeeds, but inference is denied. The team wants the documented inference role
at the resource scope without granting model-management permissions. Developers’ personal roles and
the GitHub deployment principal are separate from the runtime identity. A resource key is not part of the
approved runtime design.
Project and Search
An AI Projects Python 2.8.0 client is used for Foundry project operations, with a project endpoint and an
Entra credential. Search public access is disabled. The private endpoint exists, and the agent connection
is explicitly pinned to the named runtime principal. That principal has Search Index Data Reader for the
target index. From the runtime subnet, however, the Search hostname resolves to a public address. From
a developer laptop on another network it resolves privately and querying succeeds. The network
observations do not transfer from the laptop to the agent subnet.
Release process
A GitHub deployment workflow obtains a token using an established OIDC trust. It does not store a client
secret. The workflow principal’s project role is assigned on a different project, while its endpoint variable
points to the intended Lumen project. An authorization denial therefore needs identity and scope analysis
after authentication succeeds. Operations retain redacted request spans and release identifiers to
investigate failures. Each question asks for a single independent decision; repairing one defect is not
assumed to repair the others. A proposed change must satisfy the named runtime, region and billing facts
rather than simply resemble a working developer setup.
Diagnostic exhibit
Runtime exhibit: {"tokenAcquired":true,"inferenceRole":"Reader","searchRole":"Search Index Data
Reader","searchDns":"public address","publicSearchAccess":false}. These observations belong to the
runtime identity and subnet; the developer’s successful call uses a different network.

Case study - North support memory and response contracts
North runs a support assistant for individual subscribers. A web backend authenticates users locally and
calls a Foundry prompt agent on their behalf. Subscribers can retain preferences across sessions, ask
about current support policies and receive structured summaries. The team is testing the distinction
between stored conversation history, persistent memory and curated knowledge.
Caller and end user
All response calls authenticate to Foundry with one backend managed identity. The memory search tool is
attached to the agent and uses scope {{$userId}}. In the current implementation the backend sends no x-
memory-user-id header. The application has a verified tenant identifier and subscriber identifier in its
authenticated session. Those identifiers can be combined into a stable application-owned memory key.
The host must derive that key from the authenticated session rather than accept an arbitrary customer
identifier from a prompt.
Memory operations
The service also runs an administrative job that calls the low-level memory search API directly. The job
uses the same backend identity. It supplies a subscriber identifier in the query text but omits the explicit
scope parameter. The job must search the intended subscriber partition. Current support policy is
maintained in a knowledge store, while language and unit preferences may be distilled from
conversations. Changing a conversation title does not change either memory’s partition or the lifecycle of
the organizational knowledge.
Structured application result
The client sends requests through Responses, not Chat Completions. A summary object has ticket_id and
note properties; note accepts a string or null. Both keys must be present, and unknown properties must
be rejected by the supported strict schema. The model supports that schema. A missing note is
represented by null. The application handles refusal outcomes separately from successful objects. A
developer has copied a response_format field from a Chat Completions example into the Responses
request builder.
Behavior and monitoring
A system instruction limits the assistant to subscriber support and gives an explicit clarification path when
evidence is missing. Product staff propose replacing that instruction with a low temperature. A workflow
specialist and a retrieval specialist may also be composed, with the host retaining control of routing and
result validation. Trace spans record latency and safe user-correlation identifiers; access tokens and full
personal messages are redacted before export. These controls must be considered at their own
boundaries. Every child observation is independent and requires the fixed case facts rather than an
inferred result from a previous child.
Diagnostic exhibit
Backend exhibit: {"caller":"shared backend principal","memoryToolScope":"
{{$userId}}","memoryUserHeader":null,"directSearchScope":null}. The Responses request builder also
copied the Chat Completions response_format field; these are distinct defects against the stated per-
subscriber and output contracts.
