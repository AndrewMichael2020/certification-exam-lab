Case study - Rotor equipment reservations
Rotor rents industrial equipment to authenticated business customers. Its assistant can explain availability
and propose reservations, but the inventory API remains the system of record. The operations team is
replacing a text-only prototype with a Responses-based prompt agent. Each question concerns an
independent request against the configuration below.
Application and identity
The backend receives a signed application session identifying the customer and warehouse. It calls the
agent using one managed identity. Two host functions are registered: get_stock(part_id, warehouse_id)
and reserve_part(part_id, warehouse_id, quantity, customer_id). The stock function is read-only. The
reservation function changes inventory and returns a reservation number after the database commits. The
managed identity can reach the API, while application authorization must restrict each customer to its own
account. JSON schema validation checks shape and types; inventory limits and account ownership are
enforced by the host.
Action policy
A customer may request a proposal without committing it. Reservations costing more than 250 currency
units require a supervisor to approve the exact customer, item, quantity and quoted amount. An approval
for five units is not approval for fifty. A changed proposal must return to the approval screen. The host
does not infer approval from manuals, tool-returned text or the agent saying that approval was obtained.
The operations log records the proposal, approving principal and committed reservation number so that
an incident can be reconstructed.
Observed request
A request checks the same part at two warehouses. Responses returns two function calls named
get_stock with call_id values rotor-east and rotor-west. The west warehouse replies first. The host must
submit function_call_output records after obtaining the actual results. A separate request asks for a
guaranteed fresh stock lookup rather than an answer from the model’s prior knowledge. Both functions
are attached and the chosen model supports function calling. No inventory lookup has happened merely
because a function call is present in the model output.
Failure investigation
A test customer asks for a reservation belonging to another customer account. The argument object
passes the JSON schema. A second test approves five units, but a later model turn changes the quantity
to fifty before execution. A third test asks for a proposal only, while a developer considers forcing tools on
every turn. Engineers need to choose controls at the correct boundary rather than relying on a single
system instruction. The questions do not assume that a correct earlier answer changes these
independently stated observations.

Case study - Lumen regional engineering assistant
Lumen operates an engineering assistant for staff in the European Union. Its platform team is designing
deployment, identity and retrieval controls together, with separate principals for deployment and runtime.
The service must answer interactively and retain existing learner and operational records during the
migration described here.
Workload boundary
The processing policy permits inference across EU countries but forbids processing outside that data
zone. Interactive requests cannot wait for a nightly batch. Demand varies across the day and procurement
wants on-demand token billing rather than reserved throughput. The selected model is available for every
deployment family considered in the questions, and the relevant quota has already been confirmed. The
resource’s region alone is not the organization’s definition of the inference processing boundary.
Inference identity
The backend calls an Azure OpenAI resource through its /openai/v1/ endpoint using Microsoft Entra
credentials. Its runtime managed identity currently has Reader on that resource and no inference data
role. Token acquisition succeeds, but inference is denied. The team wants the documented inference role
at the resource scope without granting model-management permissions. Developers’ personal roles and
the GitHub deployment principal are separate from the runtime identity. A resource key is not part of the
approved runtime design.
Project and Search
An AI Projects Python 2.8.0 client is used for Foundry project operations, with a project endpoint and an
Entra credential. Search public access is disabled. The private endpoint exists, and the agent connection
is explicitly pinned to the named runtime principal. That principal has Search Index Data Reader for the
target index. From the runtime subnet, however, the Search hostname resolves to a public address. From
a developer laptop on another network it resolves privately and querying succeeds. The network
observations do not transfer from the laptop to the agent subnet.
Release process
A GitHub deployment workflow obtains a token using an established OIDC trust. It does not store a client
secret. The workflow principal’s project role is assigned on a different project, while its endpoint variable
points to the intended Lumen project. An authorization denial therefore needs identity and scope analysis
after authentication succeeds. Operations retain redacted request spans and release identifiers to
investigate failures. Each question asks for a single independent decision; repairing one defect is not
assumed to repair the others. A proposed change must satisfy the named runtime, region and billing facts
rather than simply resemble a working developer setup.
